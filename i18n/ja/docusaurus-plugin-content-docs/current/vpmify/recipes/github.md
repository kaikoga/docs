# GitHubソース

<AiGeneratedBadge />

Vpmifyは、GitHubのリポジトリのtagごとに、そのtagの時点のリポジトリの中身からパッケージのバージョンを生成します。

## 書き方

以下は、GitHubソースの書き方の例です。
レシピの `sources` 以下に書きます。

```json
{
  "type": "github",
  "url": "https://github.com/vrm-c/UniVRM",
  "tags": ">=0.131.0",
  "packages": [
    { "name": "com.vrmc.gltf", "path": "Packages/UniGLTF" }
  ]
}
```

- `type`: GitHubソースでは `"github"` です。
- `url`: GitHubのリポジトリのURLを入力します。例: `https://github.com/<owner>/<repo>`
- `tags`: （任意）レシピが読み込むリリースのバージョンの範囲を指定します。
- `packages.path`: （任意）リポジトリの中の、パッケージの場所（`package.json` のあるディレクトリ）です。省略した場合、リポジトリのルートになります。

## リリースの取得

Vpmifyにおける **リリース** とは、リポジトリのtagから生成されるパッケージバージョンの集合です。

リリースはバージョンを持ちます。
レシピがリポジトリからどのようにリリースを取得するかは、 `tagVersion` と `tags` で決まります。

### `tagVersion`

tag名は `tagVersion` の規則に従ってリリースのバージョンに変換されます。

#### デフォルトの書式

`tagVersion` が指定されていない場合、tagの名前の先頭に `v` または `V` がついていれば除去し、残りをSemVerとして読んだものが、リリースのバージョンになります。

`v1.2.3` と `1.2.3` は、いずれもバージョン `1.2.3` のリリースとして読み込まれます。
`v1.2` や `release-1.2.3` のようなtagは無視されます。

#### カスタムの書式

`tagVersion` を指定する場合、以下のように記述します。

```json
"tagVersion": {
  "match": "(\\d+)\\.(\\d+)\\.(\\d+)(?:\\.(\\d+))?",
  "version": "{1}.{2}.{3}{4:03}"
}
```

- `match`: tagの名前の全体にマッチさせる正規表現です。マッチしないtagは無視します。
- `version`: 正規表現のマッチ結果をバージョンの文字列に変換するテンプレートです。
  - `{1}` は1番目のグループを指します。
  - `{4:03}` は4番目のグループを3桁までゼロで埋めたものです。
  - マッチしなかったグループは`0`になります。

上記の例では、 tag `0.15.2.2` はリリース `0.15.2002` に、tag `0.15.2` はリリース `0.15.2000` になります。

### `tags`

`tags` が指定されていない場合、tagがマッチした全てのリリースが読み込まれます。

`tags` に [範囲](ranges.md) を指定した場合、リリースのバージョンが範囲内のものだけが読み込まれます。範囲外のバージョンは無視されます。

## パッケージの取得

Vpmifyは、リリースごとに、レシピで指定されたディレクトリの `package.json` を読み、レシピに従ってパッケージのバージョンとして読み込みます。

パッケージのバージョンは、レシピで特に指定されていない場合、 `package.json` から読まれた `version` になります。
複数のリリースが同じバージョンのパッケージを持つ場合、一番古いリリースに含まれるパッケージがそのバージョンのパッケージになります。

:::info[INFO]
あるパッケージが複数のリリースで同じバージョンを持つ場合、以下の基準でいずれかのリリースに含まれるパッケージのバージョンが選ばれます。

- バージョンが一番古いリリースに含まれるパッケージが採用されます。
- バージョンが一番古いリリースが複数ある場合、警告が出ます。
:::

## git の submodule

技術的な制約から、Vpmifyは、GitHubのsubmoduleを解決しません。
このため、submoduleが含まれるリポジトリでは、submodule内のファイルを追加で読み込む必要があります。
`overlays` で、空のディレクトリに、別のGitHubのリポジトリのcommitの中身を入れます。

以下は、パッケージ内の `VRM/MToon` ディレクトリに、 submodule の中身を追加する例です。

```json
"overlays": [
  {
    "tags": ">=0.107.0 <0.124.2",
    "path": "VRM/MToon",
    "url": "https://github.com/Santarh/MToon",
    "commit": "42b03163459ac8e6b7aee08070d0f4f912035069"
  }
]
```

- `tags`: （任意）指定した場合、リリースのバージョンが [範囲](ranges.md) 内である場合に限り適用します。省略した場合、全てのリリースに適用します。
- `path`: パッケージのルートからの相対パスで、中身の展開先を指定します。
- `url`: 中身を取得するリポジトリです。
- `commit`: 中身の commit hash です。

入れる先は空のディレクトリである必要があります。

中身の展開に失敗した場合、バージョンは生成されません。

## 1 つのリポジトリの複数のパッケージ

GitHubソースでは、1つのリポジトリが複数のパッケージを含むことができます。
`packages` に、パッケージごとの `name` と `path` を並べます。

```json
"packages": [
  { "name": "com.virtualcast.univci", "path": "Assets/VCI" },
  { "name": "com.thirdparty.effekseer", "path": "Assets/Effekseer" }
]
```

同じリリースに含まれるパッケージどうしの依存は、 `{sameTag}` で書けます（[package.jsonのオーバーライド](fix_package_json.md)）。
